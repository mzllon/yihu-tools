## BUG-001 呼出面板热键完全失效（主循环卡死）

- **日期**：2026-09-19（M3 插件基座第一期之后发现）
- **现象**：按 Alt+Space 面板再不出现；`yihu-panel status` 却显示「运行中」；合成器里面板窗口以 0×0 存在，永远画不出第一帧。主循环死后按多少次热键都只是命令入队，无人消费。
- **根因**：`sessions.rs` 的 `drain()` 处理插件 `Exited` 事件时只按插件 id 匹配会话。收起面板会杀掉全部插件会话，读线程的「已退出」事件经常**迟到**——落在下一次呼出、新一代会话已拉起之后，被误配到新一代**活会话**上，代码对活进程 `child.wait()`，主线程永久阻塞在 waitpid。插件 id 每次呼出都相同（如 `passgen`），跨代必然重名，这是匹配错误的根源。M3 之前没有会话生命周期，所以此 bug 是插件化改造引入的回归。
- **修复**：`Session` 增加代数 `gen`（每次 spawn 递增），`Exited` 事件携带 `(id, gen)` 双重匹配，旧代迟到事件直接丢弃；处理真实退出时先对进程组 SIGKILL 再 `wait()`（与 `kill_all` 同约定，有界）。
- **教训**：
  1. GTK 主循环回调里**禁止任何无界阻塞**（`wait()`/`join()`/读管道/同步 IO）。一旦卡死，所有 UI 命令静默失效，且进程不崩溃、无 panic 日志，极难察觉。
  2. 会跨生命周期重建的资源（会话、窗口、定时器回调），标识不能用业务名（id），必须带代数/序号。
  3. `status` 类旁路探针（zbus 独立线程应答）正常 ≠ 主循环正常，诊断时要查主线程 wchan（`/proc/PID/task/*/wchan`）。

## BUG-002 呼出面板先错位后跳转（历史闪烁问题复发）

- **日期**：2026-09-19（BUG-001 修复后用户复测发现）
- **现象**：热键呼出的面板先出现在错误位置（屏幕中部等），约 0.1–0.3s 后跳到正确位置。M2 期已修复过一次（`b9e9541` 窗口创建即摆放），本次复发。
- **根因**（三条机制叠加，全部经实测确认）：
  1. **回归导火索**：`3fa409f` 给定位扩展加日志时用了 `global.log`，GNOME Shell 50 已移除该 API，`_watch` 每次窗口事件都抛 TypeError，扩展的「窗口创建/尺寸变化即摆放」路径整体瘫痪，只剩守护进程的 D-Bus 兜底摆放。已改为 `console.log`（Wayland 下扩展模块要下次登录才重载）。
  2. **mutter 50 会重置摆放**：对「未确认配置就提交内容」的窗口（日志 `Buggy client ... working around`），mutter 在映射与尺寸变化时把位置重置为默认摆放，且该行为**非确定性**——映射前摆好的位置会被冲掉。
  3. **opacity=0 的 GTK4 窗口不渲染不提交**：合成器永远等不到首帧，窗口无法映射，「先摆放后显示」变成死锁；且 GTK 首次提交用的是自然尺寸（240x161），之后才校正默认尺寸（720x273），第二次配置又触发一次位置重置。
- **修复**（守护进程与扩展两端，以 Where 反馈闭环，不再用固定延时猜时序）：
  - 首帧透明度 0.0 → **0.01**（足以触发 GTK 真实渲染提交，肉眼不可见）；
  - 定位线程轮询扩展 `Where`：窗口每次尺寸变化后重新 `PlaceTop`（对应 mutter 的重置），尺寸连续稳定后才发 `FadeIn(gen)` 淡入；`gen` 为呼出代数，防迟到的淡入作用于新一代窗口；
  - 扩展缺失（Where 连续无应答 ~240ms）→ 直接淡入按系统默认位置；5s 兜底定时器（`faded` 标志去重）保证面板终会出现。
- **教训**：
  1. Wayland 客户端没有自我定位能力，「摆放」本质是守护进程 ↔ Shell 扩展的**协议**，任何一端的时序假设（固定延时、单次调用）都不可靠，必须以 `Where` 查询做闭环确认。
  2. GNOME Shell 扩展禁用 `global.log`/`log()`，用 `console.*`；扩展 JS 修改在 Wayland 下要注销重登才加载，验证时注意旧模块仍在跑。
  3. 加仪表（日志）本身也能引入回归——`global.log` 正是「加日志修闪烁观察」的提交带进来的。
  4. GUI 端到端时序问题必须实测时间线（轮询 `Where` + 墙钟戳），不能靠推理。

## BUG-003 主题切换页时间下拉无法点开（模式卡手势抢占）

- **日期**：2026-10-15（改「深色时段」配置时用户实测发现；整卡手势与下拉同为 cd9d39a「10-09 UI 重构」引入，属当时回归）
- **现象**：主题切换页「自定义时间」卡里的时间下拉（GtkDropDown）点击无反应，列表永远弹不出；「日出至日落」卡的经纬度输入框点击同样失灵。整卡点击切模式功能本身正常，故此前未察觉。
- **根因**：模式卡为「整卡可点」在整个卡片上加了 `GestureClick`，并在 `connect_pressed` 里无条件 `set_state(Claimed)` 抢占事件序列。GtkDropDown 的按钮手势**按下时只是开始识别、松开时才完成点击**——按下瞬间序列已被父卡片抢注，GTK 将该序列在其余手势中统一取消，子控件永远收不到完整点击，popup 无从打开。属「父手势 claim 吞掉子控件点击」的典型问题。
- **修复**：删掉 `set_state(Claimed)`。卡片切模式只需在 pressed 回调里 `rb.set_active(true)`，无需占用序列：点卡片空白照常切模式，点在下拉/输入框上时子控件正常接管（此时 rb.set_active 为同卡幂等操作，无副作用）。
- **教训**：
  1. 给容器加点击手势**不要 claim 事件序列**，除非确认容器内永远只放非交互内容——claim 等于把序列从其他所有手势手里夺走并取消。
  2. 「整卡可点 + 内嵌交互控件（下拉/输入/按钮）」组合上线前，必须真点一遍**子控件**，只验卡片本身可点发现不了这类回归。

## BUG-004 面板主题跟随失效（gio::Settings 被 drop 后 watch 静默退订）

- **日期**：2026-10-16（M7/W4 验收 theme-switch 插件时发现：系统已切浅色，面板仍深色）
- **现象**：面板主题只在守护进程启动时套色正确；此后系统深浅色任何变化（含插件经
  settings.write 改的）都不跟随，直到重启守护进程。
- **根因**：`watch_theme` 里 `gio::Settings` 是局部变量，函数返回 → GObject 引用计数归零
  析构 → 该实例的 dconf watch 一并退订，已连接的回调随之消失，全程无任何报错。启动时
  的首次 `apply` 仍在（启动色正确），恰好掩盖了活跟随已死。
- **修复**：`std::mem::forget` 保活（进程生命周期件，同文件 AppInfoMonitor 既有惯例）；
  回调加调试日志；另加 3s 进程内 dconf 读轮询兜底（BUG-002 同源教训：实时通知不可靠
  就轮询闭环；与 watch 共享 last 去重，避免双重套色）。
- **教训**：
  1. GObject 信号订阅随实例存亡：Rust 侧 connect 之后 wrapper 一旦 drop，订阅静默消失。
     进程级监听对象必须保活。
  2. 静默失效用「最小复现 + 调试日志」二分：最小 gio watch 程序在同环境正常 → 排除
     环境/权限，锁定面板内部；再逐层查订阅生命周期。
  3. 面板窗口懒建（首次呼出才构建）——凡是依赖窗口存在的验证（watch、轮询、UI 状态），
     测试时必须先呼出一次再触发，否则测的是空路径。

## BUG-005 插件全员零权限 + 电台五窗口 + 输入即弹窗（三因一簇）

- **日期**：2026-10-19（用户报告电台异常并附五窗截图；systematic-debugging 全程）
- **现象**：①「电台」UI 弹出五份实例且越用越多；②面板输入「电台」未经回车就自动弹窗；
  ③分类/搜索全部报「host 不在声明白名单」。收藏列表却正常。
- **根因**（三个独立缺陷叠加）：
  1. **TOML 段归属陷阱（系统性，全部 17 个 manifest 中招）**：`permissions` 写在
     `[[triggers]]` 之后，TOML 语义把它归入 triggers 子表，顶层 `permissions` 静默为空
     （serde default）→ 所有插件以零权限运行 → 一切能力请求被拒。收藏能用是因为读
     插件数据目录走沙箱挂载不经能力面。W4 的 theme-switch 也照抄了此形（当时已顺手修）。
  2. **radio.py 在 query 处理里直接弹窗**：关键词命中即 `show()`，且每次 `UI_SEQ += 1`
     换新 ui_id——每次击键/重复查询都请求开新窗。
  3. **ui.rs 按 ui_id 全局去重**：ui_id 是各插件自计数却在宿主做全局 key，永不命中 →
     一 show 一窗、只开不关；且跨插件 ui_id 撞号会误改他窗（连带隐患）。
- **修复**：
  1. 解析器 fail-loud：manifest 的 triggers 元素内检出 `permissions` 即拒载并指明错因
     （plugins.rs，附单测）；17 个 manifest 全部摆正 permissions 段位（仓库 + 装机）。
  2. radio.py 关键词查询改为出行（「📻 电台控制台」回车打开），cats 预取挪到开窗时懒加载。
  3. ui.rs 窗口去重改按插件 id（每插件一窗，重复 show 原地重建不闪窗）；close 按窗口
     身份（Rc::ptr_eq）；ui_id 改 Cell 便于原地重建时更新。
- **教训**：
  1. 声明式配置文件里「数组段之后的一切键都归该段」是 TOML 高频事故；凡可选顶层键 +
     数组段的组合，解析器必须对「键落在段内」显式拒绝，不能靠 serde default 静默吞。
  2. 新插件 manifest 是照抄现有插件写的——一个模板错误会随抄写扩散成系统性缺陷；
     解析期 fail-loud 是唯一的系统级防线。
  3. 协议字段的作用域（ui_id 属插件局部）与宿主侧 key 的作用域必须一致，跨作用域
     当全局 key 迟早撞号。

## BUG-006 WASM 共享区只增不减，长期运行插件静默失效

- **日期**：2026-10-19（W6 开发通读 SDK 时发现；W3 上线三天未爆发纯属用量尚小）
- **现象**（代码审读推演，非用户报告）：yihu-panel 是常驻守护进程，WASM 插件实例
  跨呼出复用。每次 query/能力调用都经 `alloc`/`result_field` 向 1MiB 静态共享区
  追加写入，而 `HEAP_LEN` 写指针**从无任何归零路径**——按每击键约 0.5KB 计，
  数千次击键后共享区耗尽，`alloc` 返回 -1：能力请求静默不入队、结果行静默截断，
  插件「无声失忆」，无 panic 无日志。
- **根因**：bump allocator 只分配不释放，且没有与查询周期绑定的复位点。
  协议里所有指针都是「共享区绝对地址」，盲目在任意时点归零会让仍被持有的
  绝对地址指向被覆盖的内存。
- **修复**：归零点选在 `query` 导出开头、查询文本已拷出之后（export_plugin! 宏）。
  安全性论证：此刻文本已物化为 String；随后 handle() 期间入队的能力参数、
  结果读取的追加都写在归零后的区域，且宿主读取全部发生在 query 返回之后——
  不存在跨归零点仍活跃的绝对地址。上一查询的指针在宿主 drain（读成 JSON）后
  即作废，下一次击键必然晚于本轮 drain。
- **教训**：
  1. 跨边界的 bump allocator 必须回答「指针何时失效」；WASM/宿主共享内存的
     生命周期约定要写成协议文档，不能靠双方默契。
  2. 长生命周期宿主 + 复用实例的架构下，「内存只增不减」类缺陷按每次开销看
     都微不足道，按驻留时长看必然爆发——review 时要把每次成本 × 调用频次 ×
     进程寿命。

## BUG-007 电台播放页交付与草图严重走样（封面横幅 / 控制键竖胶囊 / 播放键白底）

- **日期**：2026-10-19（W6 第二三波交付，用户对照 docs/电台native插件-草图.html 验收打回）
- **现象**：三处并现——① 封面 `GtkPicture` 被撑成全宽横幅（蜻蜓 2014 年台标是
  宽幅图，`ContentFit::Cover` 放大裁切）；② 星标/菜单键被拉成 42×60 竖胶囊，
  主播放键 58 圆倒是正常；③ 主播放键橙底没画上、白色图标在白底上不可见；
  附带 ≡ 菜单键完全吃不到 `.rp-ctl` 样式。
- **根因**（四个独立机制叠加，全部经 examples/ui_probe 探针实测定位后删除）：
  1. `GtkPicture` 的 natural 尺寸 = 图像像素尺寸，GTK 布局里没有任何容器
     能把 non-expand 子钳到 `size_request`——CSS min/size_request 只抬最低值，
     halign Center 也按 natural 分配。宽幅封面天然尺寸 > 窗口 → 横幅。
  2. 水平 `Box` 同排最高子决定排高，其余子默认 `valign=Fill` 被纵向拉伸：
     58px 主播放键把 40px 小键拉成 60px 高、radius 20 的竖胶囊。用户首张
     截图（44×76 胶囊）与 76px 旧播放键同排，完全吻合此机制。
  3. GTK 内置默认主题给 `button` 画的是 **background-image**，APPLICATION
     优先级的 `background-color` 被它整个盖住——只有加了
     `background-image: none` 才显出来。border/color/min-* 不受影响，
     所以「半生效」极具迷惑性。
  4. `MenuButton` 的可见壳是其内部 `button` CSS 节点，类加在外层
     menubutton 节点上管不到内部，需要 `.rp-ctl > button` 后代选择器。
- **修复**：① 封面字节在解码层中心方裁 + `scale_simple` 到精确逻辑尺寸
  （主 168/r20、行 40/r10），natural 恰等于目标值；② 同排小键一律
  `set_valign(Center)`；③ 所有自绘按钮补 `background-image: none`；
  ④ 补 `.rp-ctl > button` 规则。验证：探针打印 allocated 尺寸（42×42 /
  60×60）+ Xwayland 真窗截图逐项对齐草图。
- **教训**：
  1. GTK4 的「CSS 写了没生效」要先分三类：没解析（看 stderr warning）、
     被更高优先级 provider 覆盖、还是被**默认主题的另一种绘制手段**
     （image vs color）盖住——第 3 类最难猜，探针对照实验 5 分钟破案。
  2. `size_request`/`min-width` 在 GTK 里是「最低值」不是「固定值」；
     要固定尺寸必须让 natural 恰等于目标（图像预缩放）并阻断 Fill 拉伸
     （valign/halign Center）。
  3. 视觉交付必须实机截图验收，样式表「看起来对」不算数；一次性探针
     example（渲染变体 + 打印 allocated 尺寸）是定位这类问题的最快路径。

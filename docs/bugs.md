## BUG-001 呼出面板热键完全失效（主循环卡死）

- **日期**：2026-09-19（M3 插件基座第一期之后发现）
- **现象**：按 Alt+Space 面板再不出现；`yihu-panel status` 却显示「运行中」；合成器里面板窗口以 0×0 存在，永远画不出第一帧。主循环死后按多少次热键都只是命令入队，无人消费。
- **根因**：`sessions.rs` 的 `drain()` 处理插件 `Exited` 事件时只按插件 id 匹配会话。收起面板会杀掉全部插件会话，读线程的「已退出」事件经常**迟到**——落在下一次呼出、新一代会话已拉起之后，被误配到新一代**活会话**上，代码对活进程 `child.wait()`，主线程永久阻塞在 waitpid。插件 id 每次呼出都相同（如 `passgen`），跨代必然重名，这是匹配错误的根源。M3 之前没有会话生命周期，所以此 bug 是插件化改造引入的回归。
- **修复**：`Session` 增加代数 `gen`（每次 spawn 递增），`Exited` 事件携带 `(id, gen)` 双重匹配，旧代迟到事件直接丢弃；处理真实退出时先对进程组 SIGKILL 再 `wait()`（与 `kill_all` 同约定，有界）。
- **教训**：
  1. GTK 主循环回调里**禁止任何无界阻塞**（`wait()`/`join()`/读管道/同步 IO）。一旦卡死，所有 UI 命令静默失效，且进程不崩溃、无 panic 日志，极难察觉。
  2. 会跨生命周期重建的资源（会话、窗口、定时器回调），标识不能用业务名（id），必须带代数/序号。
  3. `status` 类旁路探针（zbus 独立线程应答）正常 ≠ 主循环正常，诊断时要查主线程 wchan（`/proc/PID/task/*/wchan`）。

## BUG-002 呼出面板先错位后跳转（历史闪烁问题复发）

- **日期**：2026-09-19（BUG-001 修复后用户复测发现）
- **现象**：热键呼出的面板先出现在错误位置（屏幕中部等），约 0.1–0.3s 后跳到正确位置。M2 期已修复过一次（`b9e9541` 窗口创建即摆放），本次复发。
- **根因**（三条机制叠加，全部经实测确认）：
  1. **回归导火索**：`3fa409f` 给定位扩展加日志时用了 `global.log`，GNOME Shell 50 已移除该 API，`_watch` 每次窗口事件都抛 TypeError，扩展的「窗口创建/尺寸变化即摆放」路径整体瘫痪，只剩守护进程的 D-Bus 兜底摆放。已改为 `console.log`（Wayland 下扩展模块要下次登录才重载）。
  2. **mutter 50 会重置摆放**：对「未确认配置就提交内容」的窗口（日志 `Buggy client ... working around`），mutter 在映射与尺寸变化时把位置重置为默认摆放，且该行为**非确定性**——映射前摆好的位置会被冲掉。
  3. **opacity=0 的 GTK4 窗口不渲染不提交**：合成器永远等不到首帧，窗口无法映射，「先摆放后显示」变成死锁；且 GTK 首次提交用的是自然尺寸（240x161），之后才校正默认尺寸（720x273），第二次配置又触发一次位置重置。
- **修复**（守护进程与扩展两端，以 Where 反馈闭环，不再用固定延时猜时序）：
  - 首帧透明度 0.0 → **0.01**（足以触发 GTK 真实渲染提交，肉眼不可见）；
  - 定位线程轮询扩展 `Where`：窗口每次尺寸变化后重新 `PlaceTop`（对应 mutter 的重置），尺寸连续稳定后才发 `FadeIn(gen)` 淡入；`gen` 为呼出代数，防迟到的淡入作用于新一代窗口；
  - 扩展缺失（Where 连续无应答 ~240ms）→ 直接淡入按系统默认位置；5s 兜底定时器（`faded` 标志去重）保证面板终会出现。
- **教训**：
  1. Wayland 客户端没有自我定位能力，「摆放」本质是守护进程 ↔ Shell 扩展的**协议**，任何一端的时序假设（固定延时、单次调用）都不可靠，必须以 `Where` 查询做闭环确认。
  2. GNOME Shell 扩展禁用 `global.log`/`log()`，用 `console.*`；扩展 JS 修改在 Wayland 下要注销重登才加载，验证时注意旧模块仍在跑。
  3. 加仪表（日志）本身也能引入回归——`global.log` 正是「加日志修闪烁观察」的提交带进来的。
  4. GUI 端到端时序问题必须实测时间线（轮询 `Where` + 墙钟戳），不能靠推理。

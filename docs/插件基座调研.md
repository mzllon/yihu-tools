# 插件基座调研（M3 输入）

> 时间：2026-09-18。宗旨：**性能高、资源占用率低**——本调研所有选型
> 都以「面板待命 PSS ≤ 30 MB 不因插件系统上涨、插件不用时零进程零内存、
> 呼出延迟增量可忽略」三条红线为判决标准。
> 结论先行：**插件 = 按需拉起的独立进程 + stdio 行式 JSON 协议（Alfred
> Script Filter 血统）+ manifest 声明式权限**；拒绝常驻守护进程默认态、
> 拒绝 gRPC、拒绝进程内 .so。

## 0. 结论速览

| 决策点 | 结论 | 依据 |
|---|---|---|
| 进程模型 | **默认按需拉起、即用即走**；Rust 数据型 provider 可选 socket-activation 常驻 + 空闲自退 | Rust 进程 spawn ~1–2ms、RSS ~0.3–2MB；常驻守护进程有「空闲后首开变慢」前科（elephant/Omarchy） |
| 解释型插件 | Python 可按需（~8–15MB）；**Node 按需判死**（30ms 启动 + 35–50MB），只能常驻复用且不计入待命 | 各运行时空载基线 |
| IPC | stdio 管道（小消息比 UDS 快 ~30%）；同量级，服从架构 | 小消息 ping-pong 微秒级，相对 100ms 预算可忽略 |
| 序列化 | **JSON（行式）**起步，跨语言够用（1KB ≈ 2–5µs）；Rust-only 插件可 postcard | serde_json 173–442MB/s |
| 协议蓝本 | **Alfred Script Filter JSON + uTools features/cmds + LSP 生命周期管理**的混合体 | Alfred 协议「自诞生字段级兼容」最成功；uTools cmds 五类匹配最全 |
| 权限 | **manifest 声明 + 安装时明示 + 高危动作运行时确认**（Flatpak 双层模型的轻量版）；四家竞品全部没有插件权限系统——这是我们的差异化机会 | Flatpak 静态+portal 动态双层；Raycast 靠审核+开源 |
| 隔离兜底 | 插件进程默认跑在 bwrap 白名单内（FS 白名单 + die-with-parent），低危不强制 | seccomp 对低频 syscall 插件开销可忽略 |
| 超时/崩溃 | 单查询 500ms 超时杀进程；**4 次重启/5 分钟滑动窗，第 5 次禁用**（vscode-languageclient 同款） | 行业成熟模式 |

## 1. 性能调研：进程模型 / 冷启动 / IPC / 序列化

### 1.1 进程模型

按需拉起总成本 = fork+exec ~1–2ms + IPC 握手微秒级，远低于 100ms 红线；
常驻的收益只是省这部分，代价是每进程数 MB RSS + 「空闲后变慢」风险——
walker 的数据守护进程 elephant 已有实测前科（2.20.3 升级后系统空闲时
菜单首开显著变慢，Omarchy issue #5260）。

例外通道：纯 Rust 数据型 provider 若需常驻（如剪贴板历史），用
**systemd socket-activation**（首个连接才拉起）+ `IdleAction`/自退出
实现「空闲即零内存」，不用自研守护逻辑。

### 1.2 冷启动与内存基线

| 运行时 | 启动耗时 | 空载 RSS | 按需拉起可行性 |
|---|---|---|---|
| Rust（release+strip） | ~1–2ms | 0.3–2MB | ✅ 首选 |
| Python 3 | —（秒级内） | ~8–15MB | ✅ 可按需，高频场景建议常驻复用 |
| Node.js | ~30ms | ~35–50MB（社区口径） | ❌ 按需判死；只能常驻 |

（Node 数字为社区常见口径，无权威单点出处；Python 同样无权威单点。）

### 1.3 IPC 通道

- 小消息（≤1KB）：pipe 比 UDS 快约 30%，但同为内核本机通道、微秒级；
- 大消息（1MB）UDS 反而比 TCP 慢——本场景无大消息，不构成选型因素；
- TCP loopback 明确下位（慢 2 倍以上），排除。
- **选型**：stdio 管道（实现最简、随进程生命周期自动回收）；未来常驻
  provider 走 UDS + socket-activation。

### 1.4 序列化

- serde_json 实测 173–442MB/s：1KB 消息编解码 2–5µs，可忽略；
- Rust 序列化基准（djkoloski）定性排序：rkyv（零拷贝）> bincode ≈ postcard
  > serde_json；跨语言插件用 JSON/MessagePack，纯 Rust 内部才考虑 postcard；
- **JSON 行式协议（每行一个 JSON 对象）起步**：调试友好（肉眼可读 stdio）、
  与 Alfred/生态先例一致、向后兼容易做（加字段不破坏）。

### 1.5 参照协议

- **elephant（walker）**：UDS + protobuf 自定帧（type/format/length），
  5 种消息（Query/Activate/Subscribe/Menu/State）；provider 按 Go .so
  分包、默认零数据按需安装；user 级 systemd 单元管理。
- **anyrun**：进程内 .so + `abi_stable`，插件只需 4 个函数
  （init/info/get_matches/handler）——接口极简值得学，但崩溃=宿主崩溃，
  不符合我们的隔离要求。
- **LSP**：stdio + Content-Length 帧 + JSON-RPC。教训：rust-analyzer
  1–4GB RSS——常驻+全量索引形态与 30MB 预算完全不兼容，不模仿。
  值得抄的是 **vscode-languageclient 的崩溃重启策略**：滑动窗口
  4 次/5 分钟，第 5 次进入永久禁用并提示用户。

## 2. 插件 API 生态：字段与能力面

### 2.1 manifest 要点（跨平台对照）

| 字段 | uTools plugin.json | ZTools | Raycast package.json | 一呼草案 |
|---|---|---|---|---|
| 唯一 ID | —（目录名） | name ✅ | name ✅ | `id` ✅ |
| 入口 | main（html）或 preload | main/preload（文档矛盾，可二选一=可 headless） | commands[].name 映射 src 文件 | `entry`（可执行命令） |
| 触发 | features[].cmds（字符串+五类匹配） | features 可选，cmds 五类（无 window） | commands[].mode + keywords | `triggers`（关键字 v0；regex v0.1；文件/窗口后续） |
| 结果 | mainPush 数组 | 同 | List.Item | `results[]`（title/subtitle/icon/payload） |
| 偏好 | pluginSetting | — | preferences（8 种类型） | `preferences` v0：string/bool/enum |
| 版本/兼容 | version 未记载；无宿主版本字段 | version + CHANGELOG 强制 | 无版本字段；API 版本即 npm 依赖 | `version` + `api: "^1"`（semver range，学 VS Code，**不做 GNOME 式枚举锁定**） |
| 权限 | **无** | **无** | **无** | `permissions` 声明 + 安装时明示（差异化机会） |

### 2.2 触发模型

uTools 的五类匹配指令（regex/over/img/files/window）是最全的上下文
进入模型；ZTools 去掉了 window；Raycast 用 arguments + keywords。
一呼 v0：**关键字匹配**（复用面板现有 nucleo）+ **正则匹配文本**；
files/img/window 属 M4+。

### 2.3 结果协议（Alfred Script Filter 是最佳先例）

Alfred 的 JSON 自诞生起字段级向后兼容，核心字段一呼照抄语义：
`items[]{uid,title,subtitle,icon,arg,valid,match,variables}` + 根级
`variables`（会话状态）+ `rerun`（定时自刷新）。uid 用于使用频次学习
（对应我们的 history）、`valid:false` 对应小节标题行、`match` 对应
「匹配文本与显示文本分离」（拼音索引的基础）。

### 2.4 API 面（宿主提供给插件的能力）

uTools 的 API 面 15+ 组（事件/窗口/复制/输入/系统/屏幕/用户/db/动态
指令/模拟按键/AI/ubrowser/MCP…），ZTools 同构并加 Provider（翻译/OCR）。
一呼 v0 收敛到三组：**结果输出（协议内建）+ 通知 + 剪贴板写入**；
db/storage/子进程/屏幕 等随权限模型逐期开放。

### 2.5 生命周期

uTools：进入（命中指令→展开→onPluginEnter）/退出（隐藏后台 vs 杀进程）
/单例/动态指令（setFeature/removeFeature）。一呼 v0：**每次查询拉起进程、
会话结束即退**（无隐藏后台态）；「常驻插件」走 socket-activation 例外，
属于 provider 实现细节而非协议概念。

## 3. 权限、沙箱与分发

### 3.1 权限：全部竞品都没有——这是差异化机会

uTools/ZTools/Raycast/Alfred/GNOME/VS Code/KDE 七家**全部没有插件级
权限声明系统**，兜底各显神通（人工审核、强制开源、受控 API、宿主级
系统授权）。VS Code 的教训：共享 globalState + 任意文件可读，实测
27,261 个扩展中 8.5% 存在凭据泄露风险。

一呼的最小权限集（manifest 声明 + 安装时明示 + 高危运行时确认）：
① 文件系统（默认白名单 + 用户显式选择即授权）；② 网络（声明域名或
全放行，装时明示）；③ 剪贴板读取（学 GNOME：须声明 + 用户动作触发）；
④ 子进程执行（最危险，显著提示）；⑤ 通知。低危装时明示不阻断。

### 3.2 沙箱兜底

bwrap（rootless namespaces + FS 白名单 + `--die-with-parent`）作为
不依赖插件自觉的默认收口；seccomp 对低频 syscall 插件开销可忽略
（重点是缩内核攻击面而非性能）。基线对照：Ulauncher 扩展 = 普通程序
权限零沙箱；VS Code = 进程隔离 + 受限 API 但论文证明兜底不牢。

### 3.3 分发与版本

- 分发格式：普通 zip（upx 本质就是未加密 zip，无加密必要）；
- **兼容性用 semver range（`api: "^1"`）**——GNOME 枚举式版本锁定
  每次 GNOME 升级都引发扩展大面积失效（我们亲历 OUT OF DATE），
  VS Code 的 engines range + 宿主承诺向后兼容是正确姿势；
- 市场/审核：M4 范畴。v0 先做「本地目录安装 + 中心页管理」；
  未来走「GitHub PR + 人工审核」的 Raycast/ZTools 模式。

## 4. 一呼插件协议 v0 草案（M3 规划输入）

**形态**：提供者插件（headless）= 独立进程；宿主在查询会话开始时拉起、
会话结束（面板收起/超时）即杀。

**manifest（草案）**：

```toml
id = "ip-query"
name = "IP 查询"
version = "0.1.0"
api = "^1"                      # 插件协议版本，semver range
entry = "ip-query"              # 可执行文件（插件目录内）
icon = "network-workgroup"
triggers = [
  { keywords = ["ip", "IP查询"] },
  { regex = "^(\\d{1,3}\\.){3}\\d{1,3}$", label = "查询此 IP" },
]
permissions = []                # v0 可选：fs:rw,net,exec,clipboard
```

**消息流（stdio 行式 JSON）**：

```
宿主 → 插件  {"type":"init","config":{...},"cache_dir":"..."}
插件 → 宿主  {"type":"ready","entries":n}          # 可选预声明
宿主 → 插件  {"type":"query","id":1,"text":"8.8.8.8"}
插件 → 宿主  {"type":"results","id":1,"items":[
               {"title":"8.8.8.8","subtitle":"Google DNS",
                "icon":"...","payload":"..."}]}
宿主 → 插件  {"type":"activate","id":1,"payload":"..."}
```

- 超时：单查询 500ms，超时杀进程、本会话摘除该插件并提示；
- 崩溃：滑动窗口 4 次/5 分钟，超限禁用并提示（用户可手动重启用）；
- 面板侧：结果合入现有 `PanelEntry` 流（kind 新增 "plugin"），
  历史记录 id = `plugin:<插件id>:<payload>`。

**性能门槛（M3 验收，全部可自动测量）**：

| 指标 | 门槛 |
|---|---|
| 无插件激活时面板待命 PSS | 与 M2 持平（~12.5MB，**零增量**） |
| Rust 插件进程冷启动→首结果 | ≤ 50ms |
| Python 插件进程冷启动→首结果 | ≤ 400ms（文档化，不设红线） |
| 插件进程 RSS | Rust ≤ 10MB / Python ≤ 25MB（超出即杀） |
| 呼出延迟（含插件会话建立） | 仍 < 100ms（插件查询异步，不阻塞呼出） |
| 插件未激活时 | 零进程零内存 |

## 5. 分期建议

- **M3（插件基座第一期）**：协议 v0 + 宿主会话管理（拉起/超时/崩溃策略）
  + 中心「插件」页（本地目录安装/启停/权限明示）+ 三个示例插件
  （Rust 参考实现、Python 脚本、把「切换深浅色」迁为系统插件验证协议）；
  内置能力改造为系统插件同步进行。
- **M4**：面板 UI 插件形态决策（受控 WebView 按需进程 vs 原生模板）、
  files/img/window 触发、插件市场（GitHub PR 审核）、电台 DBus、拼音索引。

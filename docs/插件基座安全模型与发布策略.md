# 插件基座安全模型与公开发布策略

> 状态：M4 安全设计基线（2026-09-20）。本文件记录公开发布前必须冻结的安全边界；它描述目标和约束，不代表当前 M3 已全部实现。
>
> 关联文档：[插件基座 M4 计划](插件基座M4计划.md)、[插件基座调研](插件基座调研.md)、[插件基座 M3 计划](插件基座M3计划.md)。

## 0. 结论先行

一呼的插件不能被当作天然可信的本地程序。公开发布时应采用以下总原则：

> **对执行环境严格，对能力接口开放；默认不信任第三方插件，默认最小权限；插件与系统的交互优先通过宿主能力代理，原生插件必须在强制沙箱中运行。**

当前 M3 的插件是独立的操作系统进程。面板在 [`tools/yihu-panel/src/sessions.rs`](../tools/yihu-panel/src/sessions.rs) 中直接执行入口，再用 stdin/stdout 交换 JSON；这带来进程崩溃隔离和生命周期管理，但**独立进程不等于安全沙箱**。当前 manifest 中的权限主要用于声明和中心页展示，不能阻止插件自行读文件、联网、访问 D-Bus 或启动其他程序。

用户还可以复制、修改或直接运行已经安装的原生插件文件。宿主只能控制由一呼托管启动的那次运行，不能凭普通文件权限或 manifest 阻止文件所有者运行自己的程序。这个边界必须在产品设计、文档、日志和市场文案中明确写出。

安全目标不是证明插件内部逻辑永远正确，而是让插件即使出现恶意逻辑或审核漏报，也无法获得超出运行时策略的系统能力，并且让受控运行的来源、版本和行为可追溯。

## 1. 当前状态与概念边界

### 1.1 M3 已有的是什么

M3 已有：

- 独立插件进程、stdio 行式 JSON 协议和 `init/query/results/activate` 生命周期；
- 进程组管理、收起时杀灭和会话代数匹配；
- manifest 解析、目录安装、启停状态和中心页权限展示；
- 激活时由宿主托管剪贴板写入的基础语义。

这些能力解决的是协议、生命周期和资源回收问题，不等于权限隔离。

### 1.2 三个容易混淆的概念

| 概念 | 含义 | 当前 M3 是否具备 |
|---|---|---|
| 独立进程 | 插件有自己的 PID、stdio 和退出生命周期 | 是 |
| 进程组管理 | 宿主可以杀掉自己拉起的进程组，避免会话结束后留孤儿 | 是 |
| 安全沙箱 | 限制进程可见的文件、网络、D-Bus、设备和系统调用 | 否 |

因此，当前插件可以作为普通程序被单独启动；它不会因为不在 `PluginMgr` 的会话表里就自动失去 Linux 用户权限。

### 1.3 不承诺什么

一呼不承诺：

- 能证明任意插件的业务逻辑绝对正确；
- 能发现所有恶意代码、后门或供应链攻击；
- 能阻止用户复制、修改或直接启动自己拥有的原生文件；
- 能为脱离一呼托管环境运行的程序承担宿主运行时保证。

一呼应承诺的是：**在一呼托管启动的运行环境中，声明外系统访问有可执行的拒绝机制，能力请求有明确边界，版本和运行事件可审计。**免责声明不能替代这些工程防线。

## 2. 威胁模型与责任边界

公开市场默认把第三方插件视为不受信任代码。以下边界必须在实现和产品文案中保持一致：

| 场景 | 一呼应提供的控制 | 责任判断依据 |
|---|---|---|
| 一呼启动的市场插件 | 强制沙箱、能力检查、资源限制、协议校验和审计 | 看包签名/hash、启动来源、沙箱状态和能力日志 |
| 一呼启动时突破承诺的沙箱 | 阻断、告警、撤销和修复 | 属于产品安全缺陷或发布配置缺陷 |
| 用户复制/修改后直接运行原生文件 | 无法替用户重新取得普通 Linux 程序的权限 | 看文件 hash、启动来源和是否存在宿主会话凭证 |
| 用户主动开启开发者模式 | 明确提示、独立目录、独立日志和不进入正式市场 | 属于用户选择的非审核运行路径，但不能用普通市场标识混淆 |
| 官方或市场构建产物被替换 | 签名校验、固定 hash、撤销和回滚 | 看签名链、构建记录和安装收据 |

“用户直接运行”不是可以靠免责声明消除的风险。若公开市场继续交付任意 ELF、Python 或其他原生代码，就必须承认它脱离宿主后仍是普通用户程序。若要求插件脱离宿主后也不能获得任意系统能力，应优先使用 WASM/WASI、声明式插件，或操作系统级强制运行环境，而不是只增加一个启动脚本。

## 3. 公开版运行时原则

### 3.1 默认拒绝与最小权限

公开版宿主托管原生插件时应至少保证：

- 插件目录只读；只有独立 `data_dir` 可写；
- 默认不挂载用户 Home、凭据目录、浏览器配置、`/proc` 敏感视图、设备节点和系统控制接口；
- 不暴露宿主会话 D-Bus、任意 Unix socket、额外继承 FD 或敏感环境变量；
- 网络默认关闭；联网须经过显式能力策略；
- 不提供通用 `exec`、任意 D-Bus 调用或任意路径写入；
- 限制进程数、内存、CPU、文件大小、标准输出和单次查询时长；
- 收起、超时、崩溃时清理整组进程和临时资源。

### 3.2 沙箱是运行时强制条件

bwrap 或等价的 namespace/Landlock/seccomp 组合应由宿主统一施加，而不是让插件自行声明“我会遵守”。公开版缺少必要隔离能力时，默认拒绝运行或拒绝安装；“明示后无沙箱降级”只能存在于明确标记的开发模式。

沙箱解决的是“插件能访问什么”，不解决“插件作者的业务意图是否善良”。因此必须与能力代理、源码/构建审查和动态探针组合使用。

### 3.3 公开市场优先使用受控运行时

公开市场的默认第三方入口应优先采用：

1. **WASM/WASI 或其他受控运行时**：宿主显式提供能力，模块脱离宿主不能自动取得文件、D-Bus、剪贴板或网络权限；
2. **声明式插件**：只描述触发条件、结果模板和有限动作，由宿主渲染和执行；
3. **受控原生 provider**：作为兼容和性能通道保留，但必须强制沙箱、签名和审计。

这不是要求第一天就把所有官方插件改成 WASM，而是公开生态不应把“可直接执行的任意原生文件”作为唯一插件模型。

## 4. 能力代理接口

### 4.1 系统交互必须窄化

插件需要剪贴板、打开 URI、启动应用、读取用户明确选中的文件、读取活动窗口摘要等能力时，应向宿主发送结构化请求，由宿主检查后代为执行。例如：

```json
{
  "type": "capability_request",
  "id": 42,
  "capability": "clipboard.write",
  "args": { "text": "要复制的内容" }
}
```

宿主至少检查：

1. manifest 是否声明该能力；
2. 用户或组织策略是否允许；
3. 参数是否符合长度、路径、URI 和目标范围限制；
4. 是否需要一次性用户确认；
5. 执行结果和拒绝原因是否写入审计记录。

建议优先提供窄接口：

- `clipboard.write(text)`，不暴露剪贴板服务 socket；
- `open_uri(uri)`，不开放任意 shell；
- `launch_app(app_id, bounded_args)`，不开放任意命令执行；
- `selected_files.read(handle)`，不开放整个 Home；
- `active_window.read_basic()`，不开放键盘记录或任意窗口窥探；
- 受限的 `network.fetch`（可选），限制协议、域名、方法、响应大小和超时。

禁止提供通用的 `exec`、任意 D-Bus 方法调用、任意路径写入和“把宿主权限整体转发给插件”的万能接口。

### 4.2 manifest 的两层含义

公共插件 API 应表达宿主能力，例如：

```toml
[capabilities]
clipboard_write = true
open_uri = true
launch_app = false
selected_files_read = false
active_window_read = false
network_fetch = false
```

`fs-read`、`fs-write`、`network` 这类字段可以作为原生插件沙箱的底层配置，但不能被解释成“插件获得了任意系统权限”。`data_dir` 是宿主自动提供的专属数据目录；剪贴板等能力不应因为一个宽泛的文件或 D-Bus 权限而被间接放开。

### 4.3 区分托管启动与直接启动

宿主可以通过一次性会话凭证、专属继承 FD 或私有 socket，把能力代理绑定到本次托管会话。凭证不得出现在命令行参数、公开环境变量或可被其他用户发现的公共路径中。插件直接启动时没有有效凭证，不能冒充一呼会话调用能力代理。

这只能阻止直接启动的程序冒用一呼能力，不能改变普通原生程序本来拥有的用户权限。要把脱离宿主后的能力也收紧到最小，必须依赖 WASM/WASI 或操作系统级强制沙箱。

## 5. 来源、源码、构建物与分发

### 5.1 市场提交源码，用户安装可验证的构建物

公开市场不应只接受一份无法追溯来源的二进制。推荐链路：

```text
源码仓库 + 固定 commit
        ↓
干净、受控的 CI 构建与扫描
        ↓
签名的插件包 + SHA-256 + SBOM
        ↓
中心校验签名并安装编译产物
        ↓
一呼沙箱/受控运行时启动
```

市场记录至少绑定以下信息：

- 源码仓库、固定 commit 和依赖锁文件；
- 构建器版本、构建参数和构建时间；
- 编译产物、包 SHA-256 和发布者签名；
- manifest、能力声明、沙箱 profile 和最低宿主版本；
- SBOM、license 信息、扫描结果和撤销状态。

源码用于审核、复现和责任追踪；编译产物用于用户安装和运行。源代码公开并不能替代运行时隔离，可复现构建也不能替代沙箱。

### 5.2 发布渠道分级

| 渠道 | 允许形态 | 必须条件 |
|---|---|---|
| 官方插件 | 签名原生或受控模块 | 可追溯构建、强制沙箱、能力最小化、可撤销 |
| 市场第三方插件 | 优先 WASM/声明式；受控原生作为例外 | 源码、固定 commit、干净构建、签名、SBOM、审核、回滚 |
| 本地开发插件 | 原生源码或未签名包 | 显式开发者模式、独立目录/命令、明显提示，不得伪装成市场插件 |

普通第三方市场拒绝“只有二进制、没有可核验源码”的包。受信渠道可以有额外政策，但仍不应绕过运行时沙箱。

## 6. 扫描与动态验证

### 6.1 中心可以扫描什么

中心或市场 CI 可以分层检查：

- manifest 字段、能力声明、包结构、路径穿越、符号链接、特殊文件、体积和压缩炸弹；
- AST/SAST：任意命令执行、敏感文件访问、D-Bus/Unix socket、动态加载、原始网络上传和混淆代码；
- 依赖漏洞、license、secret、SBOM、锁文件、构建脚本（如 Rust `build.rs`）；
- ELF/WASM 文件类型、动态库、导入符号、可疑字符串、域名、URL、setuid/capability；
- 源码 commit 与最终产物 hash/签名的对应关系；
- 版本更新相对于上一版本的代码和能力差异。

### 6.2 扫描不能证明绝对安全

静态扫描可能漏掉语义组合、依赖供应链攻击、构建环境注入、运行时下载代码和隐藏在合法功能中的数据外传。产品不得声称“扫描后绝对安全”“市场插件一定可信”或“公开源码所以没有风险”。

真正的最后防线是：即使扫描漏报，未声明的访问仍因沙箱不可达；宿主能力请求仍会被 manifest、策略和参数检查拒绝。动态探针应在无网络、最小权限环境中主动验证：未授权文件、宿主 D-Bus、任意 socket、额外进程、插件目录写入和超额资源均失败。

## 7. 审计、取证与事故处理

安装时保存安装收据，至少包含：

```text
plugin_id
version
package_sha256
publisher
signature
source_commit
registry_url
capabilities
sandbox_profile
installed_at
```

运行时记录：

```text
launch_source = yihu | developer | unknown
package_sha256
sandbox_enabled
capability_requests
capability_denials
timeouts
crashes
resource_limits
```

发生投诉或安全事件时，先根据这些记录判断：实际运行的版本和 hash、是否由一呼启动、沙箱是否启用、是否调用过能力代理、是否为用户修改后的文件。若一呼启动的插件突破了承诺的沙箱或能力边界，应按产品安全缺陷处理；若用户复制、修改后直接运行，则应能用启动来源和 hash 证明它不属于受控会话。日志不能替代修复，也不能单独决定法律责任，但能避免把所有外部程序行为笼统归因于一呼。

## 8. 公开发布前置条件与路线

### 8.1 公开 Beta 前

- 冻结威胁模型、能力命名、用户确认和拒绝语义；
- 宿主托管原生插件时强制 bwrap 或等价隔离；无隔离能力默认拒绝；
- 实现能力代理、会话凭证和越权拒绝；
- 建立安装收据、运行审计、撤销和回滚；
- 市场只接受可核验源码对应的签名构建物；
- 通过探针插件验证文件、网络、D-Bus、socket 和资源边界。

### 8.2 1.0 生态版

- 公开市场默认使用 WASM/WASI 或声明式插件；
- 原生第三方插件作为受控例外，有签名、构建证明和强制沙箱；
- 完成发布者身份、签名信任根、撤销列表和版本回滚；
- 中心展示发布者、源码 commit、能力、沙箱状态、扫描时间和风险提示；
- 保持面板呼出路径零网络 IO，市场网络只存在于中心应用。

### 8.3 实施顺序

1. 先冻结本文件中的威胁模型和能力契约；
2. 再实现强制沙箱、能力代理、资源限制和审计；
3. 再实现源码/构建物绑定、签名、ZIP 和 registry；
4. 最后扩展 UI 插件、常驻 provider 和更多系统能力；
5. 每增加一种能力，都增加 manifest 校验、代理测试、拒绝测试和取证字段。

任何阶段都不能把“审核通过”当成取消运行时隔离的理由。

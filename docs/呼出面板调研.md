# 呼出面板调研与方案（对标 uTools / ZTools / Raycast）

> 调研时间：2026-09。这是「一呼」走向呼出式工具百宝箱的第一步的调研底稿：
> UI 形态共性、GNOME/Wayland 硬限制、性能工程方案、以及本项目的落地设计。
> 所有外部数字均附来源；查不到的明确标注「未查到」，不编造。

## 0. 结论速览

1. **UI 范式有成熟共性**：固定尺寸（约 720×500）小面板、屏幕居中或上部居中、
   淡入+轻缩放瞬时动效；布局自上而下 = 搜索框 → 结果列表 →（可选）预览区 →
   提示/动作栏；交互五层：热键呼出 → 无输入默认集 → 关键字/模式触发 →
   插件面板 → Esc 逐级返回。
2. **GNOME 上有四条硬限制**（详见 §2）：Wayland 第三方应用拿不到全局热键
   （走 gsettings 自定义快捷键解决）；窗口不能自我定位（mutter 默认居中，
   接受即可）；mutter 不支持 layer-shell（gtk4-layer-shell 在 GNOME 无效）；
   GTK4 无置顶/skip-taskbar API（v1 不做置顶）。
3. **架构对齐既有原则**：新增独立执行端 `yihu-panel`（常驻守护进程 + 隐藏待命
   窗口），`yihu-panel toggle` 薄命令经 DBus 触发——这是 Ulauncher v6 /
   Flameshot 验证过的成熟模式；中心只负责注册热键、开关自启、资源总览。
4. **性能选型**：模糊匹配用 nucleo（比 fuzzy-matcher 快约 6–8 倍，helix 同款，
   多线程 + 增量快照）；列表必须用 ListView+Factory（只为可见项建 widget）；
   渲染沿用 `GSK_RENDERER=cairo`（启动器是文本+图标列表，大概率够用，实测兜底）；
   隐藏待命而非销毁重建；show 路径零 IO。
5. **竞品内存量级**：uTools ≈170 MB、ZTools ≈320 MB（均为 Electron）；
   我们的预算：**panel 守护进程待命 RSS ≤ 40 MB**（空 GTK4 窗口基线 ~20 MB，
   PSS 口径更乐观），呼出到可输入 < 100 ms，万条过滤单帧 < 16 ms。

## 1. 竞品与 UI 形态

### 1.1 横向对比

| 产品 | 技术栈 | 内存（实测口径） | 形态要点 |
|---|---|---|---|
| uTools | Electron | ≈170 MB（第三方引用） | Alt+Space 呼出居中面板；`plugin.json` 的 `features/cmds` 触发模型；插件面板初始高 544px 可动态扩展；超级面板（长按右键） |
| ZTools | Electron 41 + Vue3 | ≈320 MB（官方 issue 实测，已开优化跟踪） | 开源 MIT；uTools 模型复刻；headless 插件 + 文本/正则/全局钩子触发；Alt+Z 呼出 |
| Raycast | **原生** Swift/AppKit（非 Electron），插件跑在常驻 Node 进程 | 未查到 | 固定尺寸面板（官方未公布像素，模仿者取 750×475 量级）；命令 `view/no-view` 二元模型；Cmd+K 动作面板；Pop-to-root 超时可配（Immediately~180s） |
| PowerToys Run | .NET | 未查到 | ActionKeyword 前缀触发（`=` 计算、`?` 文件…）；居中弹出 |
| Ulauncher | Python + GTK | 每个空闲扩展 ≈16 MB+ | 顶部居中；独立进程扩展；Wayland 热键问题多，官方推荐 gsettings 自定义快捷键 |
| anyrun / walker | Rust + GTK4 | 未查到（walker 有内存增长 issue） | 依赖 **wlr-layer-shell**——GNOME 上直接不可用（见 §2） |
| fuzzel / tofi | C | 未查到（口碑最快最小） | wlroots 系专用；tofi 靠预分配内存压启动延迟 |

**量级映射**：Electron 系 150–350 MB；我们若做到待命 30–40 MB，就是数量级差异，
这正是「性能优先」立场的市场差异化。

### 1.2 UI 通用范式（各家趋同的部分）

1. **尺寸**：固定、不可自由 resize 的小窗，量级 **宽 700–770 × 高 450–550 px**；
   用户个性化交给整体缩放（Raycast Interface Size）而非拉伸。
2. **位置**：屏幕**上半区水平居中**或正中；多显示器跟随活动显示器。
3. **动效**：淡入 + 轻缩放，感知为「即时」；无厂家公布毫秒数，
   参考 NN/g：出现类动画 ≤ 250 ms。
4. **布局**：顶部搜索框（常驻焦点）→ 结果列表（图标+标题+副标题/badge）→
   可选右侧预览区（Raycast Detail；uTools 用「面板向下展开为插件面板」替代）→
   底部提示栏/动作栏。
5. **交互五层**：热键呼出/消失 → 无输入态默认集（应用/最近/剪贴板）→
   关键字或模式触发 → 二级插件面板（高度扩展或视图压栈）→ Esc 逐级返回。
6. **触发模型分化点**：纯关键字（Raycast/Alfred）→ 关键字 + regex/文本/图片/
   文件/窗口五类匹配（uTools 最全）→ 前缀符号（PowerToys）→ 插件注册 provider
   （anyrun/walker）。

### 1.3 从 uTools 借鉴什么

- **`features/cmds` 模型**：每个能力声明 `code` + `cmds`（字符串=关键字，
  对象=匹配指令：`regex`/`over`/`img`/`files`/`window`）。这套模型让
  「无输入态 → 任意上下文进入插件」成立，是插件描述的最小完备集。
- **`mainHide`**：触发后不开面板、直接执行（如转发选中文本）——轻动作不污染导航栈。
- **高度按需伸缩**（`pluginSetting.height` + 运行时 `setExpendHeight`）：
  主面板装不下富 UI 时的解法，替代 Raycast 的右侧预览区。
- **动态指令**（`setFeature/removeFeature`）：插件可运行时增删自己的关键字。

Raycast 侧再补两条：`view/no-view` 二元命令模型（轻动作直接执行）；
Pop-to-root 可配超时（关面板后导航栈何时重置）。

## 2. GNOME（Ubuntu 24.04+）硬限制与对策

| # | 硬限制 | 对策 |
|---|---|---|
| 1 | Wayland 下第三方应用**拿不到全局热键**（协议层无 grab；XWayland passive grab 也不全局生效） | **gsettings 自定义快捷键**（`org.gnome.settings-daemon.plugins.media-keys` 的 `custom-keybindings`，程序可写，需**合并**已有列表勿覆盖），command 绑 `yihu-panel toggle`。这是 Ulauncher 官方推荐路径。GlobalShortcuts portal 要 GNOME 48+，24.04 LTS（GNOME 46）用不上 |
| 2 | Wayland toplevel **不能自我定位**；mutter 默认把新窗口放屏幕中央 | **v1 接受居中**（PowerToys Run 即居中，属主流形态）；「贴顶」留给后续可选 shell 扩展 |
| 3 | **mutter 不支持 wlr-layer-shell**（已核对 mutter 源码树与 issue #973），gtk4-layer-shell 在 GNOME 无效 | 不引入该依赖；未来若做 wlroots 系适配再运行时探测启用 |
| 4 | GTK4 已删除 `set_keep_above`/`set_type_hint`/`set_skip_taskbar_hint`；Wayland 无置顶协议 | v1 不置顶：新窗口 map 时默认在顶且获焦（`focus-new-windows` 默认 `smart`），启动器场景代价很小 |

其他结论：

- **焦点**：`present()` + `entry.grab_focus()` 即可；未查到 GNOME 默认挡
  「隐藏窗口重新 present」的证据，Ulauncher 的实践证明该模式可行
  （个别残留 bug 用 wmctrl 兜底，属边缘情况）。
- **单实例唤起**：常驻 daemon + 薄 CLI 是成熟模式（Ulauncher v6：
  D-Bus activatable 单实例 + `ulauncher-toggle` 薄壳；Flameshot 同款）。
  Rust 侧用 zbus 注册 session bus name（如 `tools.yihu.Panel`），
  CLI 连总线调 `Toggle()` 后即退；可加 DBus activation 文件实现
  「daemon 未启动时自动拉起」。
- **隐藏 vs 销毁**：必须**隐藏待命**（`hide-on-close`）。销毁重建要重走
  Builder/widget 构造且 GTK4 有「销毁后内存不还」的实证；隐藏的代价是
  固定内存驻留（见 §3 预算）。
- **ESC / 失焦隐藏**：`EventControllerKey` 捕获 Escape → `hide()`；
  监听窗口 `notify::is-active` 变 false 时隐藏（注意防 hide 自触发的递归）。

## 3. 性能工程方案

### 3.1 模糊匹配：nucleo

- 选 **nucleo**（helix 同款）：官方基准比 fuzzy-matcher 快最多 8 倍、比 skim
  约 6 倍；rayon 后台线程并行；`Injector` 无锁流入 + `Snapshot` 无阻塞读取，
  支持「边输入边增量出结果」；2026-08 仍在发版，Helix 大规模在用。
- 备选 **frizbee**（SIMD，自称比 nucleo 快约 4 倍，blink.cmp/atuin 在用）：
  但 API 是每次全量重算、无增量流。万条以下 nucleo 足够，先 nucleo。
- 中文/拼音匹配是 uTools/ZTools 标配：nucleo 不做 Unicode 归一化，
  拼音索引需自建（给每个条目预生成拼音/首字母字段参与匹配，属 M3 范畴）。

### 3.2 列表渲染：ListView + Factory，cairo 兜底

- **必须 ListView**（`gio::ListModel` + `SignalListItemFactory`）：只为可见项
  建 widget 并复用；ListBox 每条目常驻一个 widget，几千条即劣化。
- factory 纪律：setup 建一次 widget，bind 只更新内容且逻辑轻
  （社区实测 bind 回调会被显著放大）。
- **渲染器**：启动器是「文本+小图标、一屏十几行」，cairo 大概率够用；
  继续沿用本项目 `GSK_RENDERER=cairo` 惯例（顺带避免 GPU 缓冲抬高 RSS 与
  部分 vulkan 驱动的秒级初始化卡顿）。**注意：cairo 渲染文本列表的逐帧
  毫秒级公开基准未查到**——实现时用真实列表自测帧时间，掉帧再评估 ngl，
  保留环境变量开关。

### 3.3 内存预算与手段

- 基线参考：空 GTK4 窗口 ≈20 MB RSS（社区实测；其中大头是共享库，
  PSS 口径更乐观）。
- 手段（按确定性排序）：① `GSK_RENDERER=cairo` 避免驱动栈映射进 RSS
  （本项目已验证，183→85 MB 的既有教训）；② 隐藏待命不销毁
  （换 <100ms 呼出）；③ 长驻进程周期性 `malloc_trim(0)` +
  限制 glibc arena（`M_ARENA_MAX`）；④ UI 延迟构建：守护态只建
  window+entry+空列表，图标缓存等在 idle 时慢加载。
- **预算**：panel 守护进程待命 RSS ≤ 40 MB（目标 ~30 MB）；每条验收见 §5。
- 反面教材：hyprlauncher 守护态被实测 ~500 MB；walker 有内存随使用增长的
  issue，社区用 systemd 内存上限兜底——常驻 launchers 的内存纪律普遍差，
  这是我们必须用数字守住的地方。

### 3.4 呼出延迟

待命态呼出路径只有四步：`present()` → 窗口获得键盘焦点 →
`entry.grab_focus()` → 首帧提交，全为本地图形栈操作（一次 Wayland 往返 +
一帧合成）。纪律：

- **show 路径零 IO**：结果集、图标、配置全部在待命时预载或在后台 idle 更新；
- 图标（尤其 SVG）解码是 launcher 冷启动的头号杀手（fuzzel 维护者原话），
  常驻方案天然规避，但仍要避免在 show 时解码；
- 无公开的业界「呼出毫秒数」基准，用本项目自测：`<100ms` 写进验收指标。

### 3.5 插件隔离模型

- 两派先例：anyrun = 进程内 `.so`（零序列化开销，但崩溃连带、Rust ABI 不稳、
  需同版本重编译）；walker/elephant = 前后端分离，UDS + protobuf
  （刻意不用 gRPC 省 HTTP/2 开销）；Raycast = 原生壳 + 常驻 Node 进程跑扩展。
- **本方案**：内置能力进程内（零开销）；**第三方插件走独立进程 + UDS
  JSON-RPC（LSP 式）**——崩溃隔离、语言无关、权限可控，符合
  README 路线图「清单 + 入口 + 权限」的插件描述方向。
  M4 前不引入，接口先在 `yihu-core` 预留描述结构。

## 4. 落地设计（yihu-panel v1）

### 4.1 架构

```
GNOME 自定义快捷键（gsettings 注册，默认 Alt+Space，合并写入勿覆盖）
        │ 每次触发
        ▼
yihu-panel toggle        ← 薄 CLI：连 session bus 调 Toggle() 即退
        │ zbus: tools.yihu.Panel / Toggle() / Show() / Hide()
        ▼
┌─ yihu-panel 常驻守护进程（GTK4，GSK_RENDERER=cairo）─────────┐
│  隐藏待命窗口：Entry(常驻焦点) + ListView(nucleo) + 提示栏      │
│  ESC / notify::is-active=false → hide()                       │
│  内置提供者（进程内）：应用(GIO AppInfo) · 一呼能力 · 计算 · …   │
│  预留：外部插件 = 独立进程 + UDS JSON-RPC（M4）                 │
└──────────────────────────────────────────────┘
        ▲ 配置 / 一键注册热键 / 开机自启 / 资源占用行
┌─ 一呼中心 ·「呼出面板」页 ─────────────────────┐
│ 中心只管配置与状态；中心关闭后面板照常工作（既有原则）│
└────────────────────────────────────┘
```

要点：与 autodark-agent 同构，是又一个**独立执行端**；中心关闭不影响呼出；
panel 退出不影响其他执行端。

### 4.2 决策清单

| 决策 | 选择 | 理由（一句话） |
|---|---|---|
| 进程形态 | 常驻 daemon + 薄 CLI | Ulauncher/Flameshot 验证；呼出 <100ms 的前提 |
| 热键 | gsettings 自定义快捷键，默认 `Alt+Space`，GUI 一键注册 | GNOME 46 唯一程序化可行路径；避开 `Super+Space`（输入法切换） |
| 窗口位置 | 接受 mutter 居中 | 硬限制；居中是主流形态；贴顶留给可选 shell 扩展 |
| 置顶 | v1 不做 | GTK4/Wayland 无客户端 API；新窗口默认在顶 |
| 匹配 | nucleo | 最快且支持增量流；frizbee 备选 |
| 列表 | ListView+Factory | 可见项复用是唯一正确做法 |
| 渲染 | cairo（保留开关） | 省内存惯例 + 文本列表场景够用；实测兜底 |
| 待命 | hide 不销毁 | 换呼出延迟；内存用预算与 trim 守住 |
| 插件 | v1 内置进程内；外部走 UDS JSON-RPC（M4） | 性能与隔离分治，与路线图插件描述一致 |
| 拼音搜索 | 预生成拼音字段（M3+） | uTools/ZTools 标配；nucleo 无归一化 |

### 4.3 里程碑

- **M1 骨架** ✅（2026-09，见[计划](呼出面板M1计划.md)）
- **M2 提供者 v0** ✅（2026-09，见[计划](呼出面板M2计划.md)）：应用启动（GIO +
  nucleo）；能力 v0（切深浅色、打开中心与各页）；算式计算；历史与默认集。
  电台播放因需中心 DBus 接口，经确认延至 M3；
- **M3 能力统一注册**：命令描述结构（清单 + 入口 + 权限）沉淀 `yihu-core`，
  面板与中心共用；拼音/首字母索引；中心电台 DBus 接口；
- **M4 外部插件 v0**：UDS JSON-RPC 协议 + 示例插件；权限提示。

### 4.4 性能验收指标（M1 起即测量并记录进 README 实测表）

| 指标 | 门槛 |
|---|---|
| panel 待命 RSS | ≤ 40 MB（**M1 实测后修正**：本机空 GTK4 进程共享库映射即 ~45 MB，RSS 口径不适用；改以待命 PSS ≤ 30 MB 为真实物理占用门槛，RSS 与中心同基线 ≤ 80 MB） |
| toggle → 可输入（暖） | < 100 ms |
| 万条过滤单帧 | < 16 ms（cairo 下实测，掉帧则评估 ngl） |
| show 路径 IO | 0（代码评审约束 + strace 抽查） |
| 常驻后台 | 1 进程（无可再省；无定时唤醒） |

> M1 实测（2026-09）：待命 PSS 25 MB ✅、暖 toggle ~10 ms ✅、
> 万条过滤 0.4–3.4 ms ✅（详见 [呼出面板M1计划.md](呼出面板M1计划.md)）。
